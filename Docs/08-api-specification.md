# API Specification

## 1. Purpose

The Psydian API layer is part of the host-side AI Bridge rather than the bare-metal kernel.

The kernel does not directly expose a conventional HTTP API in the MVP. Instead, communication is separated into two boundaries:

```text
Psydian Kernel
      ↓
Serial / Diagnostic Protocol
      ↓
Host-side AI Bridge
      ↓
HTTPS / REST API
      ↓
External AI Service
```

This separation keeps network communication outside the privileged kernel.

---

# 2. API Scope

The API specification covers the interface used by the host-side AI Bridge to communicate with the configured external AI service.

The kernel-to-AI-Bridge communication protocol is specified separately because it is a local diagnostic/communication channel rather than a conventional HTTP REST API.

The API layer is responsible for:

- Sending AI assistance requests.
- Sending structured diagnostic context.
- Receiving AI responses.
- Handling authentication with the selected provider.
- Handling validation failures.
- Handling timeouts and dependency failures.
- Preventing provider-specific details from leaking into the kernel.

---

# 3. Base Configuration

The external AI API configuration shall be supplied to the AI Bridge through environment/configuration rather than hard-coded source code.

Conceptually:

```text
AI_PROVIDER
AI_BASE_URL
AI_MODEL
AI_API_KEY
AI_TIMEOUT
API_VERSION
```

Sensitive values such as API keys must not be stored in:

- Kernel source code.
- Git history.
- Bootable kernel images.
- Public logs.

The exact variable names will depend on the selected AI provider.

---

# 4. AI Bridge Internal API

The AI Bridge should expose a small internal interface between its protocol/diagnostic layer and its provider-specific AI client.

Conceptually:

```text
Diagnostic Processor
        ↓
AI Client Interface
        ↓
Provider Adapter
        ↓
External AI API
```

Possible operations:

```text
send_request()
validate_request()
parse_response()
validate_response()
```

The exact implementation may use Rust functions, traits, modules, or another appropriate abstraction.

---

# 5. Diagnostic Request API

## 5.1 Purpose

Used when Psydian sends diagnostic information for AI-assisted analysis.

Conceptual operation:

```text
POST /chat/completions
```

The actual endpoint shall be determined by the selected AI provider.

## 5.2 Request Concept

The AI Bridge shall construct the provider-specific request from validated Psydian context.

Conceptual internal request:

```json
{
  "requestType": "diagnostic_analysis",
  "diagnostic": {
    "severity": "error",
    "subsystem": "memory",
    "message": "Heap allocation failed"
  },
  "userQuery": "Why did this happen and how should I investigate it?"
}
```

This is an internal logical model. The provider-specific HTTP request may use a different schema.

---

# 6. AI Prompt Context

The AI Bridge should construct a controlled context containing only information relevant to the requested analysis.

Possible context:

```json
{
  "system": {
    "name": "Psydian",
    "architecture": "x86_64"
  },
  "diagnostic": {
    "severity": "error",
    "subsystem": "memory",
    "message": "Heap allocation failed"
  },
  "userQuery": "Explain this error"
}
```

The bridge should not blindly forward arbitrary kernel data.

---

# 7. AI Response API

## 7.1 Purpose

Receives the response generated by the configured AI provider.

The provider-specific response may contain:

- Generated explanation.
- Suggested troubleshooting steps.
- Optional command suggestions.
- Metadata.
- Usage information.

The AI Bridge shall convert provider-specific data into a provider-independent internal response.

Conceptual internal response:

```json
{
  "type": "ai_response",
  "version": 1,
  "summary": "The kernel encountered a heap allocation failure.",
  "suggestions": [
    "Inspect allocator state",
    "Check available heap memory"
  ],
  "commands": [],
  "requiresConfirmation": false,
  "limitations": []
}
```

---

# 8. Kernel ↔ AI Bridge Protocol

The local communication boundary is intentionally separate from the external REST API.

## 8.1 Message Types

The MVP may support:

```text
AI_REQUEST
DIAGNOSTIC
AI_RESPONSE
ERROR
STATUS
```

## 8.2 Generic Message Envelope

```json
{
  "type": "diagnostic",
  "version": 1,
  "id": "diag-001",
  "payload": {}
}
```

## 8.3 Diagnostic Message Example

```json
{
  "type": "diagnostic",
  "version": 1,
  "id": "diag-001",
  "payload": {
    "severity": "error",
    "subsystem": "memory",
    "message": "Heap allocation failed"
  }
}
```

## 8.4 AI Response Message Example

```json
{
  "type": "ai_response",
  "version": 1,
  "id": "resp-001",
  "payload": {
    "summary": "The heap allocation request could not be satisfied.",
    "suggestions": [
      "Inspect allocator state"
    ],
    "commands": [],
    "requiresConfirmation": false
  }
}
```

The final protocol encoding and framing rules will be finalized during implementation.

---

# 9. Standard Errors

The AI Bridge shall use stable internal error categories so failures can be handled consistently.

Conceptual format:

```json
{
  "error": {
    "code": "AI_TIMEOUT",
    "message": "The AI service request timed out.",
    "requestId": "req-001"
  }
}
```

Possible error codes:

```text
INVALID_MESSAGE
INVALID_REQUEST
INVALID_RESPONSE
COMMUNICATION_FAILURE
AI_TIMEOUT
AI_SERVICE_UNAVAILABLE
AI_AUTHENTICATION_FAILED
AI_RATE_LIMITED
UNSUPPORTED_OPERATION
VALIDATION_FAILED
```

User-facing messages should remain understandable and should not expose API credentials, internal stack traces, or unnecessary implementation details.

---

# 10. HTTP Status Handling

When communicating with an external REST API, the AI Bridge shall handle provider responses according to their documented status codes.

General handling:

| Status | Meaning | AI Bridge Behavior |
|---|---|---|
| 200-299 | Successful response | Parse and validate response |
| 400 | Invalid request | Report request/validation failure |
| 401 | Authentication failure | Report configuration/authentication error |
| 403 | Forbidden | Report authorization failure |
| 404 | Endpoint/resource unavailable | Report configuration/provider error |
| 408 | Request timeout | Handle as timeout |
| 409 | Conflict | Handle according to provider response |
| 429 | Rate limited | Report or retry using bounded backoff where appropriate |
| 500 | Provider server error | Controlled retry/failure |
| 502/503/504 | Dependency/service unavailable | Controlled retry/failure |

Provider-specific behavior shall follow the selected API's documentation.

---

# 11. Timeout and Retry Policy

The AI Bridge shall use bounded request timeouts.

Conceptual flow:

```text
AI Request
    ↓
Start Timeout
    ↓
Provider Request
    ├── Success → Validate Response
    ├── Timeout → Controlled Error
    └── Transient Failure → Bounded Retry
```

Retry behavior should be limited to transient failures and should not create unbounded request loops.

Examples of candidates for bounded retry:

```text
429
502
503
504
network timeout
```

Authentication and malformed-request errors generally should not be blindly retried.

---

# 12. Authentication

The AI Bridge shall authenticate with the selected external AI provider using the provider's supported authentication mechanism.

Typical architecture:

```text
Environment / Secret Store
          ↓
      AI Bridge
          ↓
 Authentication Header
          ↓
   External AI API
```

API credentials must:

- Remain outside source code.
- Not be sent to the kernel.
- Not be printed in logs.
- Not be committed to Git.

---

# 13. Request Validation

Before an AI request is sent, the bridge shall validate:

- Message type.
- Protocol version.
- Required fields.
- Input length.
- Diagnostic structure.
- Supported request type.
- Context size.

Malformed requests shall be rejected.

---

# 14. Response Validation

AI responses shall be treated as untrusted external data.

The bridge shall validate:

- Response structure.
- Required fields.
- Data types.
- Allowed response categories.
- Suggested command format.
- Confirmation metadata.
- Length limits.
- Provider response status.

Conceptually:

```text
External AI
    ↓
Raw Response
    ↓
Parse
    ↓
Schema Validation
    ↓
Safety Validation
    ↓
Internal AI Response
```

Malformed responses shall not be treated as valid execution instructions.

---

# 15. AI-Suggested Command Handling

If the AI returns a suggested command:

```text
AI Provider
    ↓
AI Bridge
    ↓
Suggested Command
    ↓
Psydian
    ↓
Shell Parser
    ↓
Command Validation
    ↓
Risk Classification
    ↓
User Confirmation
    ↓
Execution
```

The API layer must never grant the AI direct command-execution authority.

---

# 16. Security Requirements

The API layer shall follow these rules:

- Never expose the API key to Psydian.
- Never embed external API credentials in the kernel.
- Validate all external responses.
- Limit the information sent to the external service.
- Use HTTPS for external communication.
- Do not trust document/system text as API instructions.
- Do not allow external responses to bypass local validation.
- Do not log complete requests when they contain sensitive data.
- Do not allow external API failures to terminate normal shell operation.

---

# 17. Rate Limiting and Resource Control

The AI Bridge should prevent uncontrolled request generation.

Controls may include:

- Maximum request size.
- Maximum response size.
- Request timeout.
- Bounded retry count.
- Provider rate-limit handling.
- Optional local request throttling.

This prevents an accidental loop in the shell or diagnostic subsystem from generating unlimited external API requests.

---

# 18. Logging and Request IDs

Each AI request should have a request identifier.

Conceptual flow:

```text
User Request
    ↓
req-001
    ↓
AI Bridge
    ↓
External API
    ↓
Response
    ↓
req-001
```

The request ID should make it possible to correlate:

- Kernel/bridge request.
- AI provider request processing.
- Validation result.
- Error.
- Final response.

Sensitive request contents should not be logged unnecessarily.

---

# 19. Health and Status

The AI Bridge should expose internal status information for diagnostics where useful.

Conceptual statuses:

```text
READY
PROCESSING
DEGRADED
AI_UNAVAILABLE
CONFIGURATION_ERROR
```

A conceptual health check could be:

```text
GET /health
```

for a future local AI Bridge HTTP control interface, but this is optional and not required for the initial MVP.

The core communication path does not depend on the bridge exposing an HTTP server.

---

# 20. API Versioning

The external provider API version should be configurable rather than hard-coded into the kernel.

The Psydian internal protocol should include its own version field:

```json
{
  "type": "diagnostic",
  "version": 1,
  "id": "diag-001",
  "payload": {}
}
```

This allows future protocol changes without requiring the entire system to be redesigned.

---

# 21. API Abstraction

The AI Bridge should provide a provider-independent interface.

Conceptually:

```text
              AIProvider
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
    Provider A Provider B Local Model
```

Possible interface operations:

```text
generate(request)
validate_response(response)
provider_name()
model_name()
```

This allows a provider to be replaced without changing the kernel communication protocol.

| ID | Requirement | Priority |
|---|---|---|
| API-001 | AI Bridge shall construct validated AI requests. | Must |
| API-002 | AI Bridge shall use HTTPS for external AI communication. | Must |
| API-003 | AI credentials shall remain outside kernel source code. | Must |
| API-004 | AI Bridge shall validate external responses. | Must |
| API-005 | AI Bridge shall handle timeout and transient failures. | Must |
| API-006 | AI-generated commands shall not bypass shell validation. | Must |
| API-007 | Requests shall have traceable identifiers. | Should |
| API-008 | Internal protocol messages shall contain a version field. | Must |
| API-009 | Provider-specific functionality shall be isolated behind an abstraction. | Should |
| API-010 | Core shell operation shall continue when the external AI API is unavailable. | Must |
| API-011 | Request and response size limits shall be enforced. | Should |
| API-012 | The bridge shall avoid logging sensitive request content. | Must |
| API-013 | The bridge shall support controlled retry behavior for transient failures. | Should |
| API-014 | The bridge shall expose useful internal status information where required. | Could |
| API-015 | The API design shall permit future provider replacement. | Should |

# 24. MVP API Boundary

For the 8-week MVP, the required API boundary is intentionally small:

```text
Psydian
   ↓
Diagnostic / AI Request
   ↓
AI Bridge
   ↓
One configured external AI provider
   ↓
Validated AI Response
   ↓
Psydian
```

Advanced features such as multiple simultaneous providers, API gateways, distributed request queues, streaming response infrastructure, and enterprise API management are future scope.

---

# 25. Important Design Rule

The external AI API is an assistance dependency, not the operating-system execution layer.

Therefore:

```text
AI API Available
      ↓
AI assistance works

AI API Unavailable
      ↓
AI assistance unavailable
      ↓
Core Psydian shell/kernel remains operational
```

This separation is a fundamental requirement of the Psydian architecture.
